# Plan 04-07 - HITL-first ambiguity handling for workshop agents

## Objective

Add a first-class clarification path so the workshop pipeline never resolves ambiguous product intent by itself. Ambiguity must pause for HITL, collect the human answer, then resume the same task from requirements/planning so the approved interpretation becomes part of the shared plan.

## Context

The current Phase 4 pipeline can ask for final PR approval, but it has no structured path for ambiguity discovered before that point. Some current behavior is too task-specific:

- `hermes-skills/workshop_coder.py` still carries OpenHarness/"12-factor" assumptions from earlier debugging.
- `workshop/reviewer.py` contains HKUDS/OpenHarness semantic checks that do not generalize across repos.
- `workshop_build.py` assumes every specialist either returns normal schema JSON or hard-fails; there is no typed control path for "needs clarification".

That creates the wrong authority boundary. Product/domain meaning belongs to the human. Agents may use repo facts and operational defaults, but they must not choose an interpretation for ambiguous requests such as "12 factory practices".

## Design

### 1. Add a requirements gate before planner

Introduce a dedicated requirements stage ahead of planner. Its output is binary:

- `ready` when the task is clear enough to plan
- `needs_clarification` when product intent is ambiguous

The gate may use reasoning to identify ambiguity and draft options, but it must not pick an interpretation. Ambiguous domain phrases always route to HITL.

Implementation shape:

- Add `workshop/requirements_gate.py` for the deterministic gate wrapper and schema handling.
- Add `skills/requirements-specialist/SKILL.md` so `run_specialist()` can invoke the gate like the other specialist roles.
- Thread clarifications into the planner input so approved answers become part of the plan context.

### 2. Add a generic clarification control type

Add Pydantic control models in `workshop/types.py`:

- `ClarificationQuestion`
- `ClarificationRequest`

Required fields:

- `task_id`
- `source_stage`
- `reason`
- `questions[]`
- `options[]`
- `allow_free_text`
- evidence/context supporting the ambiguity

`workshop/orchestrator.py` should detect `needs_clarification: true` before validating normal stage output and raise a typed control exception instead of a generic parse failure.

### 3. Update pipeline orchestration and resume flow

Extend `hermes-skills/workshop_build.py` to:

- accept `--task-id` and `--clarifications-file`
- preserve the same `task_id` across clarification resumes
- catch `ClarificationRequest`
- persist task state before exit
- emit a HITL payload with `hitl_type="clarification"`

Resume behavior must restart from requirements/planning, not jump back into coder or reviewer with a private side-message. The human answer belongs in the plan inputs shared across the pipeline.

The final push/PR approval gate remains separate and still uses `hitl_type="approval"`.

### 4. Tighten coder and reviewer behavior

`hermes-skills/workshop_coder.py`

- remove task-specific OpenHarness/"12-factor" assumptions
- convert coder no-diff or ambiguity-like outcomes into `ClarificationRequest`, unless logs show infrastructure failure
- continue to accept reviewer defect feedback only; coder never asks reviewer questions

`workshop/reviewer.py`

- delete hardcoded HKUDS/OpenHarness semantic checks
- keep generic path, syntax, test, secret, and plan-scope validation
- route ambiguity to `ClarificationRequest`, not retry feedback
- keep retry feedback limited to concrete, actionable defects

### 5. Verification

Unit and smoke coverage should prove the control path works without regressing the existing approval gate.

Required checks:

1. Requirements gate returns `needs_clarification` for ambiguous prompts like "12 factory practices", with multiple options and free-text enabled.
2. Clear tasks pass through the requirements gate without semantic drift.
3. `run_specialist()` routes clarification JSON before normal output schema validation.
4. `workshop_build.py` preserves the same `task_id` across clarification resume and restarts from requirements/planning.
5. Coder no-diff or clarification-shaped output becomes HITL clarification rather than a hang or reviewer retry.
6. Reviewer returns retryable defects for concrete issues and clarification requests for ambiguous intent.
7. Final PR approval flow still exits with the approval payload and remains push-gated.
