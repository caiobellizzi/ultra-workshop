## Summary

Phase 10.1 is a pure code + documentation phase — no new libraries, no new external dependencies. It fixes two live runtime blockers surfaced by the v1.0 milestone audit and back-fills 16 requirement entries that were promised in Phases 8 and 9 but never written.

**Blocker 1 (REQ-ws-020):** `link_orphans.py` does not exist. `cron_standard_poll._run_skill("link_orphans", entry)` logs an error and silently skips because the file is absent. The fix is a new 30-40 line stub that reads stdin JSON and calls `telegram_alert.send_alert()` — the exact same pattern `cron_bug_scan_fastpoll.py` already uses for its `post-to-telegram` dispatch path.

**Blocker 2 (dispatch mismatch):** `cron_standard_poll._dispatch_entry` calls `_run_skill("workshop_build", entry)` which pipes entry JSON to subprocess stdin, but `workshop_build.py` parses exclusively via argparse. The fix modifies only `_dispatch_entry` to issue CLI flags directly via `subprocess.run([sys.executable, skill_file, "--repo", ..., "--task-b64", ..., "--chat-id", ...])`, bypassing `_run_skill` for those two verbs. Separately, `telegram_alert.py` gets a thin `main()` that reads JSON from stdin and calls `send_alert()` to close the `post-to-telegram` subprocess dispatch gap.

**Traceability debt:** 16 requirements (REQ-ws-035..042 for Phase 8, REQ-ws-043..050 for Phase 9) were promised in REQUIREMENTS.md but never written. The content for each is derivable from: Phase 8's 08-01-PLAN.md requirement slot comments (lines 154-163), Phase 9's CONTEXT.md decisions (D-01..D-21), and Phase 9's four plan frontmatter requirement lists. No implementation needs to be re-done — only the formal traceability documents need to be written.

**Primary recommendation:** Three targeted file changes (new `link_orphans.py`, patch `_dispatch_entry` in `cron_standard_poll.py`, add `main()` to `telegram_alert.py`) plus one REQUIREMENTS.md append of 16 entries. ### Pattern 1: Stdin-JSON skill stub (link_orphans.py)

**What:** A hermes skill that reads a queue entry from stdin and calls a library function. This is the standard pattern for zero-HITL notification skills.

**When to use:** Any skill dispatched via `_run_skill()` in `cron_standard_poll.py`.

**Example (canonical model from cron_bug_scan_fastpoll.py):**
```python
# Source: hermes-skills/cron_bug_scan_fastpoll.py lines 140-144
if verb == "post-to-telegram":
    telegram_alert.send_alert(entry.get("text", "(no text)"))
```

**link_orphans.py must follow this structural template:**
```python
# Source: hermes-skills/cron_standard_poll.py + telegram_alert.py patterns
from __future__ import annotations

import json
import logging
import sys
from pathlib import Path

_HERE = Path(__file__).parent
_REPO_ROOT = _HERE.parent
if str(_REPO_ROOT) not in sys.path:
    sys.path.insert(0, str(_REPO_ROOT))

import telegram_alert  # noqa: E402

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s [link_orphans] %(message)s",
)
logger = logging.getLogger(__name__)


def main() -> None:
    """Read queue entry from stdin; post orphan list to Telegram."""
    raw = sys.stdin.read()
    try:
        entry = json.loads(raw)
    except json.JSONDecodeError as exc:
        logger.error("Invalid JSON on stdin: %s", exc)
        sys.exit(1)

    orphans: list[str] = entry.get("orphans", [])
    if not orphans:
        message = "link_orphans: no orphans in payload — nothing to link."
        logger.info(message)
    else:
        lines = "\n".join(f"- {p}" for p in orphans)
        message = f"⚠️ Orphan vault notes:\n{lines}"

    chat_id = entry.get("chat_id", telegram_alert.DEFAULT_CHAT_ID)
    telegram_alert.send_alert(message, chat_id=chat_id)
    logger.info("link_orphans: alert posted (%d orphans)", len(orphans))


if __name__ == "__main__":
    main()
```

### Pattern 3: telegram_alert.main() wrapper

**What:** A thin stdin-JSON → `send_alert()` wrapper so `cron_standard_poll` can dispatch `post-to-telegram` via subprocess without changing the existing library API.

```python
# Source: telegram_alert.py + cron_bug_scan_fastpoll.py patterns
def main() -> None:
    """Read queue entry JSON from stdin; post entry["text"] to Telegram."""
    import json
    import sys
    raw = sys.stdin.read()
    try:
        entry = json.loads(raw)
    except json.JSONDecodeError as exc:
        raise SystemExit(f"telegram_alert main(): invalid JSON: {exc}") from exc
    send_alert(
        entry.get("text", "(no text)"),
        chat_id=entry.get("chat_id", DEFAULT_CHAT_ID),
    )


if __name__ == "__main__":
    main()
```

**Constraint (D-06):** The existing `send_alert(message, chat_id)` signature is unchanged. The `main()` function only wraps it — no new logic.

### Anti-Patterns to Avoid

- **Passing `input=json.dumps(entry)` to argparse scripts:** `workshop_build.py` and `workshop_fix.py` both call `argparse.ArgumentParser().parse_args()` which reads from `sys.argv`, not stdin. Piping JSON to stdin has no effect and the entry data is silently lost.
- **Adding `import base64` to workshop_build.py:** It already imports base64 (line ~4). The `base64.b64encode` call belongs in `cron_standard_poll.py` at dispatch time.
- **Using `_run_skill()` for build/fix:** This is the root cause of Blocker 2. Any refactor that routes build/fix through `_run_skill()` re-introduces the bug.
- **Changing `send_alert()` signature:** Three+ callers depend on `send_alert(message, chat_id=DEFAULT_CHAT_ID)`. Any signature change breaks them silently.
- **Marking REQ-ws-043..050 as Complete:** Phase 9 has no VERIFICATION.md. Per D-09, status must be `Implemented`, not `Complete`.

## Common Pitfalls

### Pitfall 1: _dispatch_entry ACKs after dispatch — `link_orphans.py` must not re-ACK

**What goes wrong:** `cron_standard_poll._dispatch_entry` always calls `brain_http.mark_queue_entry_dispatched(entry_id)` after calling `_run_skill(...)` or the inline subprocess block (lines ~80-83 in the current file). If `link_orphans.py` also called `mark_queue_entry_dispatched`, the entry would be double-ACKed.

**Why it happens:** Misreading the caller/callee boundary — the dispatcher owns the ACK.

**How to avoid:** `link_orphans.py` exits 0 after posting; it does NOT call `brain_http`. The ACK is handled by `_dispatch_entry` in the caller. This matches D-03.

**Warning signs:** Any import of `brain_http` inside `link_orphans.py`.

### Pitfall 2: `_run_skill` captures stderr — CLI-dispatched subprocesses should match

**What goes wrong:** `_run_skill` uses `capture_output=True, text=True` and logs stderr on non-zero exit. If the new CLI-flag dispatch for `build`/`fix` omits capture, subprocess errors will go to the parent process's stdout instead of being logged.

**Why it happens:** The inline subprocess.run call is written from scratch without matching the existing error-logging contract.

**How to avoid:** Mirror the existing `_run_skill` error-logging pattern: use `capture_output=True, text=True, timeout=1800` and log `result.stderr[:500]` on non-zero returncode.

### Pitfall 3: `workshop_fix.py` requires `--issue-url`, not `--repo`/`--task`

**What goes wrong:** The `fix` verb dispatch mirrors the `build` verb with `--repo` and `--task-b64`, but `workshop_fix.py` argparse has `--issue-url` as the primary argument (required=True). Passing `--repo`/`--task-b64` to workshop_fix fails with argparse errors.

**Why it happens:** Assuming build and fix have the same interface. They don't — fix takes a GitHub issue URL and derives repo + task from the issue body.

**How to avoid:** Read `hermes-skills/workshop_fix.py` lines 15-19 before writing the `fix` dispatch. The queue entry for a `fix` action must carry `entry["issue_url"]`.

**Warning signs:** `workshop_fix.py` exits with a non-zero returncode citing unrecognized arguments.

### Pitfall 4: REQUIREMENTS.md traceability table breaks the "40/40 mapped" claim

**What goes wrong:** The file currently ends with `**Coverage:** 40/40 requirements mapped. No orphans.` After adding 16 new entries, this count must be updated to `56/56` (or the actual correct total), and the traceability table must include rows for REQ-ws-035..050.

**Why it happens:** The count is hardcoded, not computed.

**How to avoid:** The plan must include an explicit task to update both the traceability table rows AND the coverage count claim.

### Pitfall 5: REQ-ws-043..050 status must be `Implemented`, not `Complete`

**What goes wrong:** Marking Phase 9 requirements as `Complete` when Phase 9 has no VERIFICATION.md.

**Why it happens:** Copying the Phase 8 status without reading D-09.

**How to avoid:** Per D-09, Phase 9 requirements use status `Implemented`. Phase 8 requirements use status `Complete` (per D-08, because 08-VERIFICATION.md shows `pass_with_caveats`).

### Pitfall 6: `base64` not imported in cron_standard_poll.py

**What goes wrong:** The patched `_dispatch_entry` uses `base64.b64encode(...)` but `cron_standard_poll.py` does not currently import `base64` (verified: the import block has `datetime, json, logging, os, subprocess, sys, pathlib`).

**How to avoid:** The patch must add `import base64` to the import section.
